# Canonical Coworking Data Model

Status: normative portability model, version `1.1.0`  
Scope: operator-owned coworking business records  
Last reviewed: 2026-07-18

## Purpose and limits

This model defines separately portable coworking entities for system selection, field ownership,
integration design, migration, retention, and exit testing. It is not a production database design or
legal retention schedule. Operators must approve local fields, periods, and systems of record with the
appropriate operational and professional owners.

The portable baseline excludes card credentials, bank credentials, identity-document images,
biometric templates, passwords, API keys, door-controller secrets, and private message bodies. Store a
bounded reference or status when necessary, never the prohibited payload. Every sample in this
document is fabricated and uses reserved example identifiers or `example.invalid` addresses.

## Shared interchange fields

Every entity CSV starts with these required fields, followed by the required and optional fields in its
register row:

| Field                 | Type                   | Rule                                                                                    |
| --------------------- | ---------------------- | --------------------------------------------------------------------------------------- |
| `schema_version`      | string                 | Model version, currently `1.1.0`                                                        |
| `record_id`           | string                 | Same value as the entity's canonical identifier                                         |
| `source_system`       | string                 | Exporting system                                                                        |
| `source_record_id`    | string                 | Immutable identifier in that system                                                     |
| `created_at`          | RFC 3339 datetime      | Source creation time with offset                                                        |
| `updated_at`          | RFC 3339 datetime      | Most recent source update with offset                                                   |
| `deleted_at`          | RFC 3339 datetime/null | Tombstone time; null while active                                                       |
| `legal_hold`          | boolean                | Prevents routine deletion; only an authorized owner may change it                       |
| `retention_class`     | string                 | Operator-approved policy class                                                          |
| `data_classification` | string                 | Highest sensitivity in the row: public, internal, personal, confidential, or restricted |

Use UTF-8, RFC 4180 CSV, comma delimiters, headers, ISO `YYYY-MM-DD` dates, RFC 3339 datetimes,
decimal strings plus ISO 4217 currency, lowercase booleans, and JSON arrays inside quoted multi-value
cells. Empty means null. Email, phone, names, badge numbers, and vendor references are mutable
attributes, never canonical identifiers.

## Relationship and authority rules

- Location contains Floor; Floor contains Space; Office, Desk, Meeting room, and Event space remain
  separately identified inventory rather than generic resource subtypes.
- Person is the human identity. Member, Guest, and Staff user are separate contextual roles linked to
  Person; Company remains separate from all people.
- Lead, Opportunity, and Tour preserve distinct sales stages. Conversion links records but does not
  overwrite their history.
- Product describes a sellable item; Membership plan describes recurring service rules; Membership is
  the accepted service relationship; Agreement preserves approved terms and version.
- Booking points to exactly one typed Office, Desk, Meeting room, or Event space. Event is a program;
  Event space is physical inventory.
- Invoice owns billed amounts; Payment owns transaction events. Neither record alone authorizes
  refunds, write-offs, debt escalation, access denial, or membership termination.
- Mail item and Package remain separate custody entities. Broker, Referral partner, and Vendor remain
  distinct commercial relationships.
- Access credential and Network identity export metadata only. Secret material and biometrics are
  always excluded.

## Integration contract

Every field must have one authoritative owner even when cached elsewhere. Maintain direction, trigger,
maximum delay, approved recipients, conflict behavior, retry/checkpoint, reconciliation, manual
fallback, disable switch, retention class, and approver. Integrations must be idempotent, use canonical
IDs rather than names/emails, quarantine impossible relationships or totals, and route consequential
failures to named people. Automation must not infer contracts, consent, identity, access exceptions,
refunds, debt actions, employment decisions, safety, or legal retention.

## CSV bundle and acceptance

A complete export is a UTF-8 ZIP with `manifest.json` and all 33 named CSV files, including header-only
files for zero-row entities. The manifest records schema version, export ID/time/scope, file/entity,
row count, SHA-256, excluded payloads, and known lossy transforms. Imports run in isolation and reject
unknown required columns, duplicate canonical IDs, missing parents, invalid typed references,
impossible dates, unrecognized enums, and currency/amount mismatches.

Acceptance requires checksum and row-count validation, all foreign-key relationships, invoice/payment
control totals, active access/network reconciliation, representative record inspection, isolated
import, functional workflow tests, and written data/functional-owner sign-off. Opening a CSV is not
migration evidence.
